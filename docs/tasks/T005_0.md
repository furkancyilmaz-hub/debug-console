# T005_0 — Aşama özeti satırları

Feature: [SP005](../features/SP005.md) · Repo: debug-console
Konum: `src/features/analysis/stages.ts`
Önceki: T003_0 (aşama listesini kuran görev)

Arıza `Aşamalar` listesinde göründü. `ayrıştırma` satırı bir agent koşusunda
`2.161 sorgu · 78 istek`, diğerinde `78 istek · 2.161 sorgu` yazıyordu; üstelik
o `78`, hemen üstündeki `loglar` satırının `95 istek`iyle hiç tutmuyordu.

İki ayrı sebep var ve ikisi de `stages.ts`'in backend hakkındaki iki yanlış
varsayımından geliyor.

## Adımlar

1. **Alan sırasını ekranın kendisi belirlesin.** `stageNote` payload'ı
   `Object.entries` ile geziyordu; dosyadaki yorum bunu "backend'in JSON sırası"
   diye savunuyordu. Anahtar → etiket kaydını (`NOTE_LABEL`) sıralı bir diziye
   (`NOTE_FIELDS`) çevir, `stageNote` payload'ın sırasını hiç okumasın.
   Tanınmayan anahtarı atlama davranışı korunsun.
2. **`correlationIds`'i notta hiç basma.** O sayı `requests` ile aynı şey değil
   ve kullanıcının yapmadığı istekleri sayıyor (aşağıda). `ayrıştırma` satırı
   yalnızca `sorgu` göstersin.
3. **`truncated` bayrağını göster.** `NOTE_LABEL` yalnızca sayı okuduğu için
   `loglar` payload'ındaki `truncated: true` sessizce düşüyordu. Alanlara
   `kind: 'count' | 'flag'` ayrımı ekle, bayrak `true` iken `pencere doldu`
   parçası basılsın.
4. **Ölü tanımları temizle.** `NOTE_LABEL.calls` ve `NAME_KEYS.model` hiç
   gelmiyor — `ENRICHMENT` yalnızca `{"enriched":N}` yolluyor. `stageNote`
   docstring'indeki `892 satır · 4 ayrıştırılamadı` örneği de mockup'tan kalma;
   agent öyle bir sayı ölçmüyor (T004_0'ın aynı kararı).

`StageList.tsx` değişmiyor: satırı çizen bileşen zaten `stageNote`'un dönüşünü
basıyor, karar tamamen saf katmanda.

## Doğrulama

- Ayakta duran agent'ın SSE akışı okundu, payload'lar tel üzerinden görüldü:
  ```
  STAGE_FINISHED loglar      {"requests":95,"logLines":5000,"truncated":true}
  STAGE_FINISHED ayrıştırma  {"correlationIds":78,"queries":2161}
  STAGE_FINISHED tespit      {"findings":9}
  STAGE_FINISHED zenginleştirme {"enriched":9}
  ```
- Sıra rastgeleliği ayrı bir JDK koşusuyla kanıtlandı (aşağıdaki karar).
- `demo-crud-api`'nin `/internal/logs` ve `/internal/requests` uçları doğrudan
  çekilip iki sayaç elle karşılaştırıldı; farkı üreten `correlationId`'ler
  tek tek bulundu.
- `npm run build` ve `npm run lint` temiz.

## Tuzaklar

- **Payload sırasına güvenme.** Agent özet haritasını `Map.of` / `Map.copyOf`
  ile kuruyor; bunlar sıralı sözlük değil. Sıra gerekiyorsa ekranın kendi
  listesinden gelmeli.
- **`requests` ve `correlationIds` aynı şey değil.** İkisini aynı kelimeyle
  etiketlemek, aynı listede üst üste iki farklı sayıyı aynı şey gibi gösteriyor.
- Yeni bir payload alanı eklerken `NOTE_FIELDS`'te **sırasını da** düşün; dizinin
  yeri metnin yeri demek.

## Kararlar

**Alan sırası rastgeleydi, "backend'in sırası" değil.** Agent özet haritasını
`AnalysisEvent.stageFinished` içinde `Map.copyOf(Map.of(...))` ile kuruyor.
JDK'nın `ImmutableCollections.MapN`'i, JVM açılışında `System.nanoTime()`'dan
türetilen `SALT`'a göre yineliyor — yani JSON anahtar sırası **her agent yeniden
başlatmasında** değişiyor. Aynı iki anahtarla altı ayrı JVM koşusu:

```
[queries, correlationIds]   [correlationIds, queries]   [correlationIds, queries]
[queries, correlationIds]   [queries, correlationIds]   [queries, correlationIds]
```

Dosyadaki eski ölçüm notu `loglar {"logLines":179,"requests":8}` diyordu; bugünkü
agent aynı aşamada `{"requests":95,"logLines":5000,...}` yolluyor. Sıra artık
`NOTE_FIELDS`'ten geliyor.

**`correlationIds` gösterilmiyor — sayı yanlış değil, kullanıcının sorusunun
cevabı değil.** İki sayaç iki ayrı kaynaktan geliyor:

| | kaynak | ne sayıyor |
|---|---|---|
| `requests` | `app_log`'ta `REQUEST_COMPLETED` ile başlayan satırlar (`RequestQueryService`) | tamamlanmış gerçek HTTP istekleri |
| `correlationIds` | ayrıştırılan SQL satırlarındaki farklı `correlationId` (`AnalysisService.correlationIds`) | SQL üreten her istek |

`demo-crud-api`'nin `CorrelationIdFilter`'ı `/internal/` ve `/swagger-ui`
yollarına bilerek `REQUEST_COMPLETED` yazmıyor (`isNotRecorded`), ama o
isteklerin Hibernate SQL'i `app_log`'a düşüyor. Sonuç: **ajanın kendi
`/internal/logs` + `/internal/requests` çağrıları — yani önceki analizler —
`correlationIds`'e giriyor, `requests`'e girmiyor.** Ölçümde fazladan çıkan
`correlationId`'nin satırlarında `REQUEST_COMPLETED` yoktu ve bağ değerleri
`[WARN] [ERROR] [5000]` idi; bu, `/internal/logs`'un kendi seviye süzgeci ve
`limit`i.

Ters yönde de sapıyor: log penceresi 5.000 satırda dolunca SQL satırları
kesiliyor ama `requests` ayrı sorgu olduğundan kesilmiyor (90 dakikalık
pencerede `95 istek` / `78 correlationId`), ve hiç SQL üretmeyen istekler
`correlationIds`'e zaten girmiyor.

Bu bir agent hatası değil, iki sayacın farklı tanımı. `reportView.ts`'teki
`cleanRequestCount` de aynı asimetriyi `Math.max(0, …)` ile karşılıyor. Ekran
bunu düzeltemeyeceği için göstermiyor; mockup'ta da `ayrıştırma` satırının ikinci
slotu istek sayısı değildi (`871 sorgu · 4 ayrıştırılamadı`).

**`truncated` aşama satırına eklendi.** `ReportSummary` kırpılma uyarısını zaten
basıyor (T003_0 sonrası eklenmişti) ama o uyarı ancak analiz bitince çıkıyor —
model açıkken 20 saniye sonra. Aşama satırındaki `pencere doldu` parçası aynı
bilgiyi ilk saniyede veriyor.

## Sonuç

Aşama satırları artık şöyle okunuyor:

```
loglar          5.000 satır · 95 istek · pencere doldu
ayrıştırma      2.161 sorgu
tespit          9 bulgu
zenginleştirme  9 zenginleştirildi
```

`npm run build` ve `npm run lint` temiz. Değişen tek dosya `stages.ts`;
`StageList.tsx`, `analysisStream.ts` ve `src/api/` katmanı elden geçmedi —
`payload`'ın ham `unknown` durup gösterim katmanında daralması, arızayı tek
dosyada bitirmeye yetti.
